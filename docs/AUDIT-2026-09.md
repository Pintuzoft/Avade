# Avade – genomgång september 2026

Genomgång av hela kodbasen (ca 36 000 rader) mot bahamut, källkod från
[DALnet/bahamut](https://github.com/DALnet/bahamut). Nätverket kör idag 2.1.4, och
senaste release är 2.2.4 (2024-10-04).

**Mål: bahamut 2.2.4**, med bibehållen funktion mot 2.1.4 som nätverket kör idag.
Bahamut 3.0 är inte släppt, så del 4 är bara information inför framtiden.

- **Del 1** – buggar samt kompatibilitet med det ni kör idag (2.1.4).
- **Del 2** – framåtkompatibilitet 2.1.4 → 2.2.4.
- **Del 3** – ny funktionalitet som services behöver för att kunna använda det ircd:n erbjuder.
- **Del 4** – Bahamut 3.0 (Gossip + IRCv3), ej släppt: endast information, inget vi bygger för nu.

Status: [ ] = ej åtgärdad, [x] = åtgärdad (1–12 `security-fixes`, 26–32 `topic-sync`, 68 `charset-utf8mb4`, 51 `nickipstr`, 17/59/N0/N1/69 `vop-hop`, 13/70 `sessions`, 14–16 `reconnect`, 45/47 `stability`, 24/33–44 `functional-fixes`, 19–21/23/71 `bans-and-matching`, 22/25/49/50/72/73 `cleanup`, N14 `vhost`, N2 `svsclone`, 52/N5/74 `chanflags`, N6/N7 `spamfilter-svstag`). Radnummer avser commit `511c0db`.

> Obs: `Handler.process` fångar alla `Exception`. En NPE eller AIOOBE kraschar alltså
> inte services, men kommandot avbryts tyst (användaren får inget svar) och ibland
> blir tillståndet halvt uppdaterat.

# DEL 1 – Buggfixar & kompatibilitet med 2.1.4

## 1.1 Access & säkerhet (högst prio)

- [x] **1. Användare med access kan göra sig själv till SOP, även om de är AKICK:ade.**
  [CSExecutor.java:1992](../src/chanserv/CSExecutor.java#L1992)
  - Villkoret `!ci.isAtleastSop(ni) && !ni.is(ni2)` släpper igenom handlingar på sig själv, och nivåkontrollen (rad ~1998) hoppas då över.
  - `ChanInfo.getNickByUser` (345–377) returnerar även nicks som bara står på AKICK-listan.
  - Resultat: `SOP #chan ADD <eget nick>` befordrar användaren, och AKICK-posten tas bort via `removeFromAll`.
  - Fix: tillåt självundantaget bara för `DEL`, och kräv minst AOP.
- [x] **2. ACCESSLOG kräver inte identify (regression i 511c0db).**
  [CSExecutor.java:1928](../src/chanserv/CSExecutor.java#L1928)
  - `NickServ.findNick(user.getName())` används istället för `ci.getNickByUser(user)`, och `ni.isAtleast(SA)` istället för `user.isAtleast(SA)`.
  - Den som bär ett AOP- eller staff-nick oidentifierad kan läsa accessloggen, medan en SA som är identifierad under ett annat nick nekas.
- [x] **3. TOPICLOG saknar accesskontroll.** [CSExecutor.java:1634-1668](../src/chanserv/CSExecutor.java#L1634), 1940–1952
  - Konfen säger SA-nivå, men `ChanServ.enoughAccess` anropas aldrig, så alla kan läsa topic-historik för alla kanaler (även +s/+p).
  - `return` saknas efter "Database not available".
  - Grenen för SYNTAX_ERROR dereferenserar en null `getChanInfo()`.
- [x] **4. NEVEROP ignoreras vid join.** [ChanServ.java:284](../src/chanserv/ChanServ.java#L284)
  - `ni.is(NEVEROP)` jämför nicknamnet med strängen "NEVEROP". Ska vara `ni.isSet(NEVEROP)`.
- [x] **5. DYNAOP (ny funktion) saknar kontroller.** [ChanServ.java:861-925](../src/chanserv/ChanServ.java#L861)
  - `findNick(user.getName())` kontrollerar inte identify, varken för den som oppar eller den som blir oppad.
  - Den kringgår NOOP.
  - `addAccess → removeFromAll` tar tyst bort en AKICK-post.
  - En AOP kan deoppa en annan AOP och därmed ta bort den från listan.
- [x] **6. Throttle är trasig.** [Throttle.java:79](../src/core/Throttle.java#L79)
  - Uttrycket `- this.lastHit < range*1000` saknar `now()` och är därför alltid sant.
  - Tidig `return` när `hits > maxhits` uppdaterar `lastHit` innan reset-koden nås, så spärren blir permanent. Vem som helst kan låsa ute ett nick eller en kanal från IDENTIFY tills omstart.
  - Lyckade försök räknas också.
  - GHOST ([NSExecutor.java:1132-1150](../src/nickserv/NSExecutor.java#L1132)) har ingen throttle alls, så lösenord kan bruteforcas.
  - IDENTIFY/DROP med ett argument (rad 1099: `!ni.is(user)` är alltid falskt) throttlas aldrig.
  - Fix: `now() - lastHit`, reset före tidig return, räkna bara misslyckade försök, och throttla GHOST och DROP.
- [x] **7. Lösenord läcker i klartext till snoop-kanalen.**
  - CS DROP ([CSExecutor.java:473-501](../src/chanserv/CSExecutor.java#L473)) maskerar bara vid lyckat försök.
  - CS REGISTER (347–375) läcker på alla felvägar.
  - NS DROP maskerar bara när `cmd.length == 5`.
  - Fix: maskera innan `validateCommandData`.
- [x] **8. Varje rå IRC-rad skrivs till stdout, inklusive `IDENTIFY <lösen>`.** [Handler.java:180](../src/core/Handler.java#L180)
- [x] **9. RootServ kontrollerar aldrig `enoughAccess`.** Vilken SRA som helst kan lägga till och ta bort SRA:er, trots att texten säger att bara master får det. [RSExecutor.java:131-181](../src/rootserv/RSExecutor.java#L131)
- [ ] **10. Lösenord lagras reversibelt.** `AES_ENCRYPT` används med en gemensam nyckel (SECRETSALT), och GETPASS visar hela historiken i klartext.
  - Förslag: bcrypt/argon2 med migrering, och ta bort GETPASS.
  - `Hash.md5` använder en delad statisk `MessageDigest` (inte trådsäker) och tappar inledande nollor.
  - Auth-tokens är md5 av tiden istället för `SecureRandom`.
- [x] **11. DEOP saknade nivåkontroll: en AOP kunde deoppa SOP och founder.** (MDEOP hade redan kontrollen.) Samtidigt fixad: NICK_NOT_PRESENT i OP/DEOP kraschade.
- [x] **12. NS DROP ignorerar MARK** (CS DROP kontrollerar den).

- [x] **26. Kolon-bugg (bekräftad i test).** `Topic` gör `replace("^:", "")`, vilket är bokstavligt och inte regex.

- [x] **29. Fel setter.** `user.getString(FULLMASK)` används istället för `data[3]` som bahamut skickar.
  - Det kan visa en riktig host för hostmaskade användare.
  - bahamuts "samma topic"-kontroll matchar aldrig.
- [x] **30. Topic skickas på varje join, oavsett KEEPTOPIC.** `doSJoin` anropar `sendTopic`, och `doChan` skickar dessutom två gånger när kanalen skapas.
  - Services är U-lined, så bahamut skriver alltid över (ingen TS-kontroll). Nyare topics återställs, och folk ser "ChanServ changed the topic".
  - Fix: skicka bara när kanalen skapas och KEEPTOPIC eller TOPICLOCK är på, samt när TOPICLOCK nekar en ändring.
- [x] **31. `checkTopic` ger NPE** när TOPICLOCK är på och ingen topic finns sparad.
- [x] **32. Server-TOPIC (burst, efter split) uppdaterar aldrig ChanInfo.**

> Topic-fixarna är testade mot riktig bahamut 2.2.4 + MySQL 8: topic sparas utan kolon
> och med IRC-tid, ingen TOPIC skickas vid join, KEEPTOPIC återställer med originalsetter
> och -tid, bursten skriver inte över nyare topics, varje kanal laddas med sin topic efter
> omstart och TOPICLOCK återställer. TOPICLOG visar nu de senaste 100 (visade förut de äldsta).

- [x] **68. Teckenkodning: åäö/emoji kan inte sparas (upptäckt under test).**
  - Avade läser socketen med Javas standardteckenkodning (UTF-8 från Java 18), men alla tabeller är `latin1`.
  - Latin1-bytes från äldre klienter blir `�` och tecken utanför latin1 (emoji ☕ m.m.) går inte att lagra. MySQL avvisar då hela skrivningen: *Incorrect string value* (topic, memo, beskrivningar, snooplogg …).
  - Den misslyckade posten ligger dessutom kvar i arbetskön och försöks om och om igen (se #46).
  - **Åtgärdat på `charset-utf8mb4`:**
    - IRC-rader tolkas som UTF-8, med cp1252 som reserv för gamla latin1-klienter, och skrivs alltid som UTF-8.
    - JDBC använder `utf8mb4`.
    - DB 1.2609-2 konverterar alla tabeller till `utf8mb4_swedish_ci`, efter att AES-kolumnerna (`chan.pass`, `passlog.pass`, `maillog.mail`) först gjorts om till `varbinary` så att krypterade lösenord och mail behålls byte för byte.
    - Testat på MariaDB 10.8.8 med latin1 som standard: både uppgradering av befintlig data och ny installation.
    - Kvar: att poster som misslyckas permanent ska kastas eller loggas (#46).

- [x] **69. UNBAN/INVITE/WHY räknade AKICK som access** (hittat under VOP/HOP-arbetet).
  - `getNickByUser` returnerar även nick på AKICK-listan, så en akickad användare kunde UNBAN:a och INVITE:a sig själv förbi sin akick.
  - Nu kräver UNBAN och INVITE AOP+ (som i ircd:n, där bara op får ta bort bans och invita), och WHY kräver VOP+.
  - Dessutom: AKICK WIPE och wipe av maskposter rensade aldrig databasen, så listorna kom tillbaka efter omstart.
- [x] **70. Master sätts bara vid `LUSERSLOCK`** (`doFinishSync`), som bahamut bara skickar från hubbar.
  - Om Avade länkar till en server utan hubbflagga blir master aldrig satt, och `sendSpamFilter` körs inte heller.
  - Fix: kör det när synken är klar (andra PING, se `Handler.isSynced()`).

- [x] **71. SQLINE och SGLINE ADD har aldrig fungerat** (hittat under test).
  - Valideringen krävde `nick!user@host` för alla bantyper, men SQLINE är ett nick- eller kanalmönster och SGLINE ett realname-mönster.
  - `expireToDate` ignorerade dessutom tidsenheten helt: `30d` blev 30 minuter, `1h` blev 1 minut, och spamfilter-akills varade därför 30 minuter istället för 30 dagar.
  - **Åtgärdat på `bans-and-matching`:**
    - En gemensam tolkare för tidslängder (tal = minuter, eller `m`/`h`/`d`/`w`/`y`, i `long`).
    - Säker wildcard-matchning (escapad, skiftlägesokänslig och åt ett håll när användardata jämförs).
    - Range-triggern bannar rangen.
    - Testat live: SQLINE på `{Bob}` och AKILL på 60 dagar.

- [x] **72. Avade startade även om nick och kanaler inte gick att läsa in.**
  - Inläsarna gav en tom eller halv lista vid fel. Avade länkade ändå, tog bort `+r` från alla, bytte folk till Guest-nick och deoppade. `fixMaster` försökte dessutom skapa master-nicket på nytt.
  - **Åtgärdat på `cleanup`:**
    - Avade väntar på databasen innan länkning.
    - Om inläsningen misslyckas är Avade passiv: inga `-r`, inga Guest-nick, ingen deop, kick eller modelock, ingen DYNAOP, inga topic-ändringar och ingen `fixMaster`. NickServ, ChanServ och MemoServ svarar "loading".
    - Nya försök görs var 30:e sekund, och därefter kopplas services-ID in och alla användare och kanaler kontrolleras.
    - Testat live genom att döpa om `nick`-tabellen: ingen deop och inga Guest-byten. När tabellen kom tillbaka laddades allt, och founder var fortfarande identifierad.

- [x] **73. Webb-AUTH med fel kod räknades som lyckad** (hittat under test).
  - `NSDatabase.authMail`/`authPass` returnerade `true` oavsett om koden stämde.
  - Databasen ändrades inte, men Avade skickade "verifierad" och loggade AUTHMAIL. Vid PASS avidentifierades dessutom alla på nicket.
  - Nu räknas uppdaterade rader.

- [x] **74. Chanflags överlevde inte en omstart** (hittat under #52).
  - I konstruktorn i CSFlag fick NO_QUIT_MSG värdet från NO_PART_MSG, EXEMPT_WEBIRC skrevs över av HIDE_MODE_LISTS och NO_NICK_CHANGE av NO_UTF8.
  - CSChanges spårade inte MAX_INVITES, MAX_MSG_TIME, NO_QUIT_MSG, EXEMPT_WEBIRC, HIDE_MODE_LISTS, NO_NICK_CHANGE och NO_UTF8, så de sparades aldrig.
  - MAX_MSG_TIME validerade flaggans namn istället för värdet, och MAX_INVITES gav inget svar.
  - **Kanaler registrerades med `max_invites = 0`, som efter en omstart skickades till ircd:n och stängde av `+I`-listan.** DB 1.2609-5 rättar befintliga kanaler.
  - Testat mot ircd:n med `CHECK CHANNEL` efter omstart.

## 1.6 Kompatibilitet med 2.1.4 (funktioner som redan finns i ircd:n)

- [x] **51. IPv6: ingen `CAPAB` skickas.** [ServSock.java:129](../src/server/ServSock.java#L129)

# DEL 4 – Bahamut 3.0 (Gossip + IRCv3) – framtid

Källa: branch `bahamut-mods-gossip` i DALnet/bahamut (34 commits, 2026-03-12 → 2026-07-23,
version 3.0.0 i patchlevel.h). **Ej mergad, ej taggad, ej släppt.** Senaste release är
fortfarande 2.2.4.

**Vad det är:**
- **Gossip:** nytt server-till-server-protokoll där servrarna bildar ett mesh istället för hub/leaf. Varje händelse (`GEVENT`) får ett unikt ID och skickas till alla peers. Det blir inga kaskad-splits, och när en peer försvinner ligger dess användare kvar.
  - Länkarna kräver TLS och ett delat lösenord (`gopeer {}`).
  - Konfliktregler: äldst TS vinner för nick, nyast `topic_time` vinner för topic.
- **TS5-brygga (`m_legacy_bridge`):** gamla `connect {}`-länkar fungerar fortfarande, och **services ansluter via TS5 + U:line som idag**.
- **IRCv3:** ett 20-tal capabilities, bland annat account-tag/notify, extended-join, chghost, server-time, message-tags, chathistory, resume, MONITOR, STARTTLS och WebSocket.
- **Inbyggda services byggdes och togs sedan bort**, till förmån för externa services som Avade.

**Kontrollerat i källkoden – det här påverkar Avade:**
- [x] **B1. CAPAB är borttaget.** BURST, UNCONNECT, **NICKIPSTR** och NOQUIT tvingas på alla länkar.
  - NICK skickar därför **alltid IP som sträng** (`1.2.3.4`, IPv6 eller `0.0.0.0`).
  - **Avade kan inte ta emot en enda användare**, eftersom `Long.parseLong(data[9])` i [User.java:63](../src/user/User.java#L63) kastar.
  - Samma fix som #51, så gör den en gång och gör den rätt.
- [ ] **B2. TOPIC-setter är alltid `nick!user@host`.** Se #29.
- [ ] **B3. NOQUIT:** inga QUIT per användare vid SQUIT, så services måste själva ta bort användarna bakom servern. Hänger ihop med #16.
- [x] **B4. Användare från gossip-noder** kommer via bryggan med IP `0.0.0.0`, servicestamp `0` och umode `+`.
  - Klon-triggern och akill-logik måste ignorera `0.0.0.0`, annars kan Avade AKILL:a `*@0.0.0.0` och träffa alla sådana användare.
- [ ] **B5. Radlängden** är fortfarande 512 mot services (2048 gäller bara mellan gossip-noder).

**Begränsningar i ircd:n just nu** (inte Avades fel, men bra att veta):
- SVSNICK, SVSMODE, SVSHOST, SVSHOLD, SVSXCF, SF, SVSCLONE och SJR sprids **inte** över gossip.
- NOTICE från services når inte användare på andra gossip-noder.
- `+r` från services sprids inte.
- I ett blandat mesh fungerar services alltså bara fullt ut för användare på den nod services är länkade till. Det bör rapporteras upstream.
- **SASL finns inte** på 3.0-branchen. Ett tidigt utkast finns på branchen `ircv3-support` (2025): `AUTHENTICATE` skickas till en SaslServ-alias, och services svarar `SASL … SUCCESS|FAILED`. Det kompilerar inte och är inte mergat.
- **Kontonamn:** account-tag, account-notify och extended-join annonseras men är alltid tomma. Det finns inget kommando för services att sätta konto (`account_name` skrivs aldrig).

**Möjligheter för Avade** (när eller om upstream definierar protokollet):
- N10: SASL PLAIN/EXTERNAL (SaslServ).
- N11: kontonamn (föreslå upstream t.ex. `SVSACCOUNT` eller `SVSMODE nick ts +r <konto>`).
- N12: CERTFP-inloggning, där fingeravtrycket visas i WHOIS (numeric 276).
- N13: SVSHOST ger nu chghost till IRCv3-klienter.
